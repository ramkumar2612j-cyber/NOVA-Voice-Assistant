## Findings (no code change unless stated)
- SecureStore (AES-256-GCM, Keystore key, random IV): LOW - blob not bound to its slot (no AAD), only matters with access to app-private prefs. LOW - decrypted values cached in memory for the process. INFO - no StrongBox request; if the Keystore key is lost (factory/lock-screen reset) getKey returns "" silently and the user must re-enter keys. Slot names from the page are now restricted (together/hf) and capped.
- UpdateManager: GOOD - https only, host allow-list, redirects re-checked, size + SHA-256 must match the feed, APK must be same package, higher versionCode and same signing certificate before PackageInstaller (Android also enforces it). MEDIUM (design) - the SHA-256 comes from the same feed as the file, so for "skills" and "model" items a malicious FEED OWNER is trusted (the user picks the feed URL; feed host is auto-allowed). APK is protected by the signature check. Skill packs still pass addSkill safety rules (max 100). Advice: only use your own feed. LOW - InstallResult PendingIntent is FLAG_MUTABLE with an explicit component (needed by PackageInstaller).
- GitHubPublish: token only in the Authorization header, redirects off, login validated, repo name slugged; creates a PUBLIC repo (publish is confirmed in the UI by an earlier rule). MEDIUM (user risk) - a classic token with `repo` scope is broad: advise a fine-grained token limited to new repos. Endpoints written from docs, never run against GitHub.
